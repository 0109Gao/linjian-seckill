## 四、4 个缺陷的实测证据与修法

### D1（P0）雪花 ID 精度丢失

**证据链（三步闭环）：**

```
DB 真实值     109597783211638784   ← 订单已成功落库，status=0 待支付
前端 URL      109597783211638780   ← 末位被改
对照实验      换成 …784 访问 → 结果页正常显示「抢购成功」
```

管理端同样中招：订单表把 `userId 2116113282478075906` 渲染成 `2116113282478076000`。

**根因**：`Long` 值 1.09e17 / 2.1e18 远超 `Number.MAX_SAFE_INTEGER`（9.007e15），`JSON.parse` 静默截断。

**修法**（一处改，两处受益）：

```java
@Configuration
public class JacksonConfig {
    @Bean
    public Jackson2ObjectMapperBuilderCustomizer longToString() {
        return builder -> {
            builder.serializerByType(Long.class, ToStringSerializer.instance);
            builder.serializerByType(Long.TYPE, ToStringSerializer.instance);
        };
    }
}
```

> 为什么之前没发现：约 1/16 的 ID 恰好落在可精确表示的格点上，W4 冒烟和 JMeter 都用了 curl（curl 不改数字）。

### D2 退出登录后顶部不刷新

**证据**：登出后 `localStorage.accessToken = null`，但 `.user` 元素数量仍为 1，登录按钮 0 个；刷新后才恢复（.user=0，登录按钮 2 个）。

**根因**：`isLogin: () => !!localStorage.getItem(TOKEN_KEY)` 是 Pinia getter（底层 computed），依赖的不是响应式数据 → 结果被永久缓存。

**修法**：

```js
getters: {
  isLogin: (state) => !!state.user || !!localStorage.getItem(TOKEN_KEY)
}
```

`state.user` 是响应式依赖，`clear()` 里 `this.user = null` 会触发重算。

> 顺带修正之前报告的一处误判：**登录后顶部是正常刷新的**（登录页无 layout，跳转后 layout 重新挂载，getter 首次求值即正确）。真正失效的只有「同一 layout 内登出」。

### D3 详情页返回退到 about:blank

**证据**：新开标签直接访问 `/user/activities/1001`，`history.length = 2`，点返回后 URL 变为 `about:blank`，body 为空。

**修法**：不要裸用 `router.back()`：

```js
function goBack() {
  if (window.history.state?.back) router.back()
  else router.push('/activities')
}
```

`result.vue` 的「返回上一页」有同样问题。

### D4 前台商城硬编码 5173

**证据**：点击后新窗口 URL = `http://localhost:5173/user/`；而实际部署在 80 端口的 nginx 下，5173 是开发服务器端口，线上必然打不开。

**修法**：改为相对路径 `window.open('/user/', '_blank')`。

### 修复过程中的两个设计决策

**1. 为什么不用 `ToStringSerializer` 一把梭**

最初方案是 `serializerByType(Long.class, ToStringSerializer.instance)`，把所有 Long 都输出成字符串。
实现后发现副作用：分页返回的 `total`（Long）会变成 `"308"`，而前端有
`v-if="total > pageSize"` 与 `el-pagination :total` 两处依赖数字类型。

改为自定义 `LongSafeSerializer`：**仅当值超出 ±9007199254740991 时才写字符串**。
雪花 ID 恒为大数、分页/库存/数量恒为小数，行为稳定且不破坏既有计算。
验证 V2 专门盯着这一点：`"total":308` 仍是数字。

**2. 为什么没改 `el-radio-button :value="null"`**

控制台残留一条 Element Plus 提示：
`[el-radio] [API] label act as value is about to be deprecated in version 3.0.0, please use value instead`。

来源是筛选栏的「全部」用了 `:value="null"`，组件内部把它当作未定义并回退到 label。
**功能完全正常**（筛选 4 项用例全通过），且它是第三方库的向前兼容提示，不是本项目的逻辑错误。
若要消除，需要把「全部」的取值从 `null` 改成 `-1` 或 `'all'` 并在请求层转换，
等于为了消一条日志去动筛选语义，风险大于收益，因此保留并在文档中记录。

### 测试脚本自身的两个问题（不是产品 bug）

**① `has-text` 子串匹配导致误点**

`admin.spec.js` A18 只想验证「取消活动有二次确认弹窗」，写了
`button:has-text("取消")` —— 而弹窗确认按钮文案是 **「确认取消」**，
子串匹配先命中它，于是**真的把活动取消了**（唯一的待开始活动被清掉，
导致后续 U14 筛选用例假失败）。

修复：改用 `button:has-text("再想想")`（取消按钮文案）精确匹配。
验证：跑完 A18 后活动状态零变化。

**② 筛选断言硬编码历史数据**

U12 写的是 `txt === '全部' ? after === 2`，当时活动只有 2 个。
演示数据扩到 5 个活动后直接假失败。

修复：改成真正校验语义 —— 卡片上的状态标签必须与所选 tab 一致：

```js
const tags = (await page.locator('.card .el-tag').allTextContents()).map(s => s.trim())
const expect = { 全部: null, 进行中: '进行中', 即将开始: '待开始', 已结束: '已结束' }[txt]
const ok = expect === null ? after > 0 && after === totalNum : after > 0 && tags.every(t => t === expect)
```
