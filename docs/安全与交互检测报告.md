## 一、结论摘要

| 等级 | 数量 | 说明 |
|---|---|---|
| 严重（Critical） | 2 | 可直接接管后台 / 核心业务链路失效 |
| 高危（High） | 1 | 跨用户越权读取订单 |
| 中危（Medium） | 3 | 暴力破解可行、参数无边界、令牌无法吊销 |
| 低危 / 体验 | 6 | UI 状态、跳转硬编码、交互语义 |

**总体评价**：架构与并发设计是扎实的（Lua 原子预扣、幂等表、条件更新关单、对账只修超卖方向），
权限边界在**后端**做得很干净（管理接口 403、越权支付 403、订单列表按 userId 隔离）。
但存在 2 个**必须修**的致命问题：一个是配置默认值导致的后台接管，一个是前端大整数精度导致的秒杀结果链路失效。
后者是本次检测最重要的发现——它会让真实用户在浏览器里抢到商品却看不到结果。

## 二、严重问题（必须立即修复）

### C1 · 默认 JWT 密钥可伪造管理员令牌，直接接管后台

**位置**
- `backend/seckill-web/src/main/resources/application.yml:86`
- `docker/docker-compose.full.yml:111`

```yaml
jwt:
  secret: ${JWT_SECRET:linjian-seckill-jwt-secret-key-please-change-in-production-2026}
```

**问题**：密钥默认值硬编码在仓库里。部署时若未设置 `JWT_SECRET` 环境变量，攻击者拿仓库源码即可
自行签发任意用户的 token。系统只按 token 里的 `username` 查库取角色，因此只要知道管理员用户名
（默认就是 `admin`），无需密码即可获得 ADMIN 权限。

**实测复现**（已成功，非理论推断）：

```bash
# 用仓库里的默认密钥手工签发 HS384 token，payload 只要 username=admin
FORGED=$(node -e "..." )   # 见下方脚本
curl -s -o /dev/null -w "%{http_code}" http://localhost/api/admin/goods -H "Authorization: Bearer $FORGED"
# → 200
curl -s -X POST http://localhost/api/admin/activities/1001/preheat -H "Authorization: Bearer $FORGED"
# → 200  （写操作同样放行）
```

实测返回了完整商品列表，预热写接口也返回 200。**攻击者未持有任何账号密码，却拥有完整后台权限。**

**修复建议**

1. 生产部署强制要求密钥，缺失则启动失败（不留默认值）：
```java
// JwtProperties 增加校验
@PostConstruct
void validate() {
    if (secret == null || secret.length() < 32
        || secret.contains("please-change-in-production")) {
        throw new IllegalStateException("JWT_SECRET 未配置或仍为默认值，拒绝启动");
    }
}
```
2. `application.yml` 改为 `secret: ${JWT_SECRET}`（无默认值），本地开发放 `application-local.yml`（已在 .gitignore）。
3. `docker-compose.full.yml` 改为 `${JWT_SECRET:?JWT_SECRET is required}`，缺失即报错。
4. 建议把 `role` 也写入 token claim 并在过滤器校验，避免"改了数据库角色但旧 token 仍是旧权限"，
   同时配合短有效期。

### C2 · 雪花 ID 超过 JS 安全整数，前端精度丢失导致秒杀结果页永远拿不到订单

**位置**
- 后端：`SeckillResult.requestId/orderId`、`OrderVO`、`AdminOrderVO` 等所有 `Long` 字段直接以 JSON 数字返回
- 前端：`frontend-user/src/views/order/result.vue:102`、`detail.vue:240`、`api/index.js:35`

**问题**：雪花 ID 量级约 `1.1e17`，远超 JS `Number.MAX_SAFE_INTEGER`（`9.007e15`）。
`JSON.parse` 后末位被静默改写，前端拿着错误的 id 去轮询，后端查不到 → 一直返回 PENDING。

**实测证据（同一笔订单）**

| 来源 | requestId |
|---|---|
| 数据库 / Redis 真实值 | `109592827096203264` |
| 前端 URL 实际发出的值 | `109592827096203260` |
| 差值 | **4** |

```bash
# 前端实际发的 id → 查不到
curl /api/seckill/result/109592827096203260  → {"status":"PENDING"}
# 数据库真实 id → 正常
curl /api/seckill/result/109592827096203264  → {"status":"SUCCESS","orderNo":"SK202610307096203264"}
```

订单**已经落库成功**（DB 库存 100→99、`sk_bought` 有记录），但用户在结果页看到的是
「正在为你排队」→ 轮询 30 次 → 「结果确认中」。**用户以为没抢到，实际上抢到了**，
极易引发重复下单投诉或超时未支付自动关单。

**影响范围（全部失真，已逐一验证）**

```
orderId   2116108540641243138 → JS 2116108540641243100  失真
userId    2116107731127988226 → JS 2116107731127988200  失真
requestId 109592827096203264  → JS 109592827096203260   失真
```

即：管理端订单表格里的「用户 ID」列显示的也是错的值；任何把 id 回传后端的场景都不可靠。

**为什么之前 UI 冒烟没发现**：只有约 1/16 的 id 恰好落在大整数可精确表示的格点上。
之前用 curl 测试（curl 不改数字）全部成功，掩盖了问题；用真实浏览器才复现。

**修复建议（推荐方案一）**

方案一：全局把 Long 序列化为字符串（改动最小、最彻底）
```java
// JacksonConfig 里注册
@Bean
public Jackson2ObjectMapperBuilderCustomizer longToString() {
    return builder -> {
        builder.serializerByType(Long.class, ToStringSerializer.instance);
        builder.serializerByType(Long.TYPE, ToStringSerializer.instance);
    };
}
```
前端随之把 id 当字符串处理：路由参数 `params.requestId` 本就是字符串，无需改动；
但 **不要** 再对它做 `Number()` / `parseInt()` 转换。

方案二：仅对暴露给前端的 VO 字段加注解
```java
@JsonSerialize(using = ToStringSerializer.class)
private Long requestId;
```
需覆盖：`SeckillResult.requestId/orderId`、`OrderVO.id`、`AdminOrderVO.orderId/userId/requestId`、
`ActivityVO.id`、`ActivityGoodsVO.activityGoodsId/goodsId`。

**回归用例**：修完后必须用**真实浏览器**跑一次完整抢购，确认结果页 3 秒内变 SUCCESS，
且 URL 里的 requestId 与数据库完全一致（不能只看 curl）。

## 三、高危问题

### H1 · 秒杀结果查询越权（IDOR），可读取他人订单号

**位置**：`SeckillService.java:116-131`

```java
public SeckillResult queryResult(Long requestId, Long userId) {
    SeckillResult cached = resultCache.get(requestId);   // ← 没有校验 userId
    if (cached != null) {
        return cached;                                   // 直接返回他人结果
    }
    SkSeckillOrder order = orderService.findByRequestId(requestId);
    ...
    if (!order.getUserId().equals(userId)) {             // 只有回落 DB 时才校验
        throw new BizException(ErrorCode.FORBIDDEN);
    }
```

**实测**：用户 B 用用户 A 的 requestId 查询，拿到 A 的完整订单信息：

```
用户 A 自己查 → {"status":"SUCCESS","orderId":2116107737130037249,"orderNo":"SK202610303593385984"}
用户 B 查同样 id → {"status":"SUCCESS","orderId":2116107737130037249,"orderNo":"SK202610303593385984"}
```

**可利用性**：requestId = 时间戳 + 序列号，高度可预测（同一毫秒内连续递增）。
结合 C2 的精度问题，实际可枚举的 id 空间被进一步压缩。

**注**：越权**支付**是安全的（`OrderService.pay` 有 `userId` 校验，实测返回 403），
订单列表也按 userId 隔离（B 查不到 A 的订单）。问题只在这一处。

**修复**：缓存里存 userId 并在返回前比对，或结果键改为 `sk:result:{userId}:{requestId}`：
```java
public SeckillResult queryResult(Long requestId, Long userId) {
    SeckillResult cached = resultCache.get(requestId);
    if (cached != null) {
        if (!userId.equals(cached.getUserId())) {   // 新增 owner 字段
            throw new BizException(ErrorCode.FORBIDDEN);
        }
        return cached;
    }
    ...
}
```

## 四、中危问题

### M1 · 登录接口无失败计数与锁定，可无限暴力破解

实测连续 10 次错误密码全部正常返回，无任何限流、锁定或验证码。

```bash
for i in $(seq 1 10); do curl -X POST /api/auth/login -d '{"username":"qaauser01","password":"wrongpass"}'; done
# 10 次全部 200，无延迟、无锁定
```

密码策略仅 6~64 位（`RegisterRequest`），配合默认管理员密码 `123456`，风险叠加。

**修复**：同一用户名/IP 连续失败 5 次锁定 15 分钟（Redis 计数）；管理员账号强制改初始密码。

### M2 · 分页参数无上限，pageSize 可传 1000000

```bash
GET /api/activities?pageSize=1000000  → 200（0.012s，当前数据量小）
GET /api/seckill/orders?pageSize=999999 → 200
GET /api/activities?pageNum=-1        → 200
GET /api/activities?pageSize=0        → 200（返回空 list，total 仍为 2）
```

当前数据量小看不出问题，数据量上去后是内存与慢查询风险。

**修复**：`@RequestParam(defaultValue="10") @Max(100) long pageSize`，并对 `pageNum >= 1` 做校验。

### M3 · 登出后 Access Token 仍然有效（无吊销机制）

`AuthService.logout` 只删 Redis 里的 refreshToken，accessToken 在 2 小时有效期内继续可用。
代码注释已声明这是刻意取舍，但对"账号被盗后立刻踢下线"的场景是硬伤。

**修复**：低保真方案——Redis 存 `jwt:blacklist:{jti}`（TTL = token 剩余有效期），
过滤器里检查一次；或把 accessToken 有效期压到 15 分钟。

## 五、低危与体验问题

### L1 · 用户端退出登录后顶部不刷新，仍显示用户名（原判定已修正）

> **修正说明（2026-10-30 18:40，Playwright 实测）**：本段初版判定为「登录后顶部不刷新」，
> 经逐项实测该结论**不成立** —— 登录发生在独立的 `/login` 页（无 layout），跳转后 layout
> 重新挂载，getter 首次求值即正确，顶部能正常显示昵称。真正失效的场景是**同一 layout 内退出登录**。

**位置**：`frontend-user/src/store/user.js:14`

```js
isLogin: () => !!localStorage.getItem(TOKEN_KEY),   // getter 无响应式依赖
```

Pinia getter 底层是 computed，而 `localStorage` 不是响应式数据 → 结果被永久缓存。

**实测证据**：

| 步骤 | `.user` 元素 | 「登录」按钮 | localStorage.accessToken |
|---|---:|---:|---|
| 登录后 | 1 | 0 | 有 |
| 点「退出登录」后 | **1** | **0** | **已清空** |
| 手动刷新后 | 0 | 2 | 已清空 |

即：token 已清、请求已失效，但界面仍显示头像和昵称，用户会误以为自己还在登录状态。

管理端不受影响，因为它的布局用的是依赖 `state.user` 的 `displayName`。

**修复**：
```js
state: () => ({ user: null, loaded: false, token: localStorage.getItem(TOKEN_KEY) }),
getters: { isLogin: (s) => !!s.token },
actions: {
  setLogin(d) { ...; this.token = d.accessToken },
  clear() { ...; this.token = null }
}
```

### L2 · 管理端「前台商城」硬编码开发端口 5173

**位置**：`frontend-admin/src/layout/index.vue:89`

```js
window.open('http://localhost:5173', '_blank')
```

生产由 nginx 在 80 端口同时托管 `/user/` 与 `/admin/`，5173 是 Vite dev server 端口，
容器化部署下不存在。实测该地址返回空内容，点击后是空白页。

**修复**：同源相对跳转即可 —— `window.open('/user/', '_blank')`。

### L3 · 详情页「返回」直接访问时会退出站点

`detail.vue:3` 用 `@back="router.back()"`。若用户从外部链接/新标签直接打开详情页，
历史栈为空，`back()` 会把用户带离本站。建议判断 `history.length` 后回落 `/activities`。

### L4 · 活动卡片「立即抢购」按钮靠事件冒泡跳转

`list.vue:37-44` 的按钮没有 `@click`，靠父级 `.card` 的 `@click="goDetail"` 冒泡生效。
实测点击后确实跳转到详情页（功能正常），但按钮文案是「立即抢购」而行为是「看详情」，
语义误导；且一旦有人给按钮加上 `@click.stop`，跳转立即失效。

**建议**：按钮显式写 `@click.stop="goDetail(item.id)"`，或把文案改成「查看详情」。

### L5 · 中间件端口直接映射到宿主机

`docker-compose.full.yml` 虽未显式映射 3306/6379/5672，但容器网络内中间件无密码
（Redis 无 `requirepass`、MySQL root 密码为 `123456789`、RabbitMQ 为 `seckill/seckill123`）。
一旦加上端口映射或部署在可访问网段，即为数据泄露面。

**建议**：Redis 设置 `requirepass`；所有口令改为 env 注入；生产不映射中间件端口。

### L6 · CORS 允许 localhost 任意端口

`SecurityConfig.java:93` `setAllowedOriginPatterns(List.of("http://localhost:*", "http://127.0.0.1:*"))`
且 `allowCredentials(true)`。当前无 Cookie 鉴权，危害有限；上线前应收窄为具体域名。
